# 文本关联、索引与版本差分

适用于档案、地图调查文本、任务阅读内容以及相关漏收录/误标排查。下述路径与函数是项目中的追踪入口，使用时重新读当前实现；既有适配逻辑不等于游戏运行行为已经得到证明。

## 从文字追踪到交互

按问题追踪完整证据链：

```text
界面文字 → I18nTextTable 的精确文本 ID
         → DialogTextTable / PrtsReading 等业务记录
         → LevelData 交互配置 / LevelScriptData 动作引用
         → 对话顺序、条件、分支及所属关卡
```

- 两句文字相邻、共享 ID 前缀或数字后缀连续，只能支持候选分组。证明同一次交互中的前后文，优先找交互物/动作实际引用的对话 ID，以及有序内容列表或明确的后继关系。
- 读取脚本图时区分顺序执行、条件分支、回调和退出事件；记录入口与边的字段路径。共用节点、环和多个入口不能简单展开为唯一线性对话。
- `plugin/js/v3-archive.js` 的 `dialogLineIndex()` 当前按 `dlg_..._<数字>` 分组、数值排序。这是展示适配约定；检查命名例外、缺号、重复序号及引用不存在的分组。缺号不自动意味着正文丢失，匹配失败也不能静默丢弃。
- 只用 `DialogTextTable` 可以建立候选文本段，不能独自证明哪些段在地图可交互、归属哪个交互物或执行条件。因此需要区分“文本内容库”和“实际引用范围”。
- 每一小段对话可作为展示条目、首句作为标题，但身份保留来源路径及对话 ID。相同文字或相同 dialogId 在不同地点出现时，按用户要求区分“去重对话数”和“交互实例数”。

## 空正文与漏收录的定位

按“原始记录 → 引用解析 → 本地化 → 标准化 → 收录过滤 → 渲染”逐层检查，报告首次丢失的位置：

1. 记录是否存在于所选版本，列表中是否有多个子条目；不要只看聚合页或首条内容。
2. `contentId`、覆盖字段和目标记录是否存在；标题存在不证明正文引用有效。
3. 文本对象的内嵌 `text` 为空时，检查精确文本 ID 与对应语言表，不把尚未水合的引用判为空内容。
4. 内容是否属于另一种已支持载体，例如 `RadioTable` 的字幕、富文本或图片；取不到某种正文不等于整个条目无内容。
5. 检查类型过滤、去重键、索引覆盖和 UI 条件，避免为单个条目增加固定 ID 白名单。

项目曾针对 `text_` 内容引用补充对应 `radio_` 的查找。复用前检查 `v3-archive.js` 中的内容解析和 `overrideRadioId` 等实际优先级，并确认候选目标存在、有匹配内容。前缀替换不是任意表之间都成立的协议；未知命名应报告未解析。

## 地区与素材归属

- 从条目所引用关卡出发，检查 `LevelDescTable` 及其关联表的真实地区键，再解析地区名称；记录各跳字段。关卡名、地区名和地图文件夹名并不自动等价。
- 地图 ID 前缀可作为候选线索，不能替代地区外键。多地区引用保留多值；无法关联的条目归为未确定，不凭标题猜地点。
- 分类图标是产品展示约定，与数据关系证据分开记录。不要把本项目的统一图标扩展成其他业务的素材识别规则。

## 少量文件读取与可扩展索引

先检查用户允许使用的索引的实际结构；只有名称而无路径或内容时询问，不自造协议。

- 当前入口：`tools/ake-data-tool/ake_tool/asset_index.py` 负责提取资产元数据，`plugin/js/v3-archive.js` 的 `mapTextRecords()` 消费 `datasets.json.files[path].meta.narrativeDialogIds`。LevelScriptData 阅读引用的字段需另查提取器和消费者，不能沿用 LevelData 字段猜测。
- 索引覆盖全部相关路径且元数据完整时，一次读索引，筛选包含目标引用的记录，再按需读关联表或源文件。若索引已含足够的引用与表内正文，列表阶段可以无需读取逐个 LevelData；要求游戏行为证据时仍需回到源配置。
- 区分空数组（已扫描但无目标引用）和缺字段（未扫描、旧结构或无效）。索引不完整时不能声称“没有此类交互物”；报告覆盖缺口，按授权决定补扫或刷新索引。
- `*_lv_data_sub_env*.json`、`*_lv_data_sub_<任务编号>.json` 可辅助定位，但不能作为完整收录白名单。新地图和其他命名必须能通过路径枚举与内容元数据进入范围；历史“40 个文件”等计数仅为当时快照。
- 发布工具的增量逻辑也需处理旧索引缺少新元数据的情况：源文件未变不代表索引无需补齐。检查生产者、消费者和完整性判定是否一致；索引升级不要求在整个 Json 数据集上记录“覆盖游戏版本”。分析任务本身不授权上传或更新远端索引。

## 语义版本差分

分别回答三个问题：索引负责“收录哪些内容”，业务表负责“条目及引用是否变化”，本地化/渲染负责“用户看到什么”。一个来源的差分不能冒充另外两个来源的历史。

- 记录当前/基线的游戏版本、Hotfix、语言、来源及可用状态；不要混用网站版本、TableCfg 版本与 Json 共享 revision。跨游戏版本比较还是逐 Hotfix 比较由任务指定，不固定某个历史版本为所有功能的基线。
- 本项目地图文本/任务文本曾明确要求使用 `DialogTextTable` / `PrtsReading` 比较，并保留资产索引。查看 `dialogSignatures()`、`readingEntrySignatures()` 和版本选择逻辑：任务条目的稳定身份为 `sourceId:listId`，对话按 dialogId 聚合；这些键与算法仍需对当前数据核对。
- 比较原始、规范化的业务字段；分别定义身份、排序、正文引用及实际内容的变化。对象键顺序可规范化，具有业务顺序的数组不得随意排序；不要将路径、缓存元数据或临时展示字段混入内容签名。
- 标题由空引用补全、语言回退改变或显示文本水合，不应在未定义语义时自动算正文修改。若只比较两张业务表，同一文本 ID 对应的语言表正文单独修改可能检测不到；明确这一覆盖限制，不能宣称比较了全部可见文本。
- 新增要求基线可用且稳定身份确实不存在；修改要求身份相同且选定语义字段不同。删除需要基线与当前收录范围均完整。加载失败、缺表与合法空表分开处理；基线不可用时停用相应差分，不把所有当前记录标成新增。
- 解释“为什么被标记为修改”时，给出同一稳定身份的前后字段值、签名包含的字段和导致差异的具体项，并说明是否影响正文。仅说 JSON 不同不足以解释标记。
- 以某个游戏版本为初始版本、不显示该版本已有条目的新增，是产品规则；记录适用功能，不把历史要求的 `1.4.4` 或“只存在新增”泛化到所有数据。

## 交付证据

按任务需要提供“来源文件/记录键/字段路径 → 引用目标 → 解析结果”，并附：覆盖范围、未知或异常记录、计数单位、版本基线与未确认部分。对规则给一个正常样本和实际发现的反例；没有发现反例时说明检查范围，不虚构例外。
